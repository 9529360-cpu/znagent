# 查健康数据汇总（本地导出文件）

## 适用场景

- 用户问最近走了多少步、运动了多久、某天消耗了多少、心率怎么样。
- 用户说“帮我看看这周的健康数据”“昨天睡得怎么样”。
- 用户给了一个健康导出文件（Apple Health 的 `export.xml`、本地传感器记录），想知道里面有什么。

## 隐私边界（硬规则）

- **只读本地、数据不出机**：三个工具只打开用户指定的本地文件并解析，整个过程不联网、不上传、不调用任何外部服务。这是连接器模块级的保证（`device_health_connector.py` 不导入任何网络栈），不是口头承诺。
- 用户问“帮我把数据发给某某分析”“上传到云端”时：拒绝，明确说 ZN 不会把健康数据传出本机；可以建议用户自己用原 App 的分享功能。
- 用户没有给文件、也没配置默认文件时：明确说还没看到任何健康数据，不要编造数字。

## 查汇总（读，只读不审批）

1. 默认用 `device_health.summarize` 查汇总。`days` 按用户问的范围填（没说就填 7，最多 90）；`end` 缺省是今天。
2. 按返回的 `day` 逐日念：步数、距离（km）、主动消耗（kcal）、锻炼分钟、心率（平均/最低/最高）。心率为 null 时说“这天没有心率记录”，不要估。
3. 同一天的 `watch_activity_summary` 是手表/设备自己报的日合计，拿来和记录汇总交叉核对：两者差得离谱时如实说“记录汇总和设备自报对不上”，不要自行取舍。
4. 窗口内某天没有记录时明确说“这天没有数据”，不要填 0 假装测过（0 步和没数据是两回事）。

## 查指标清单与明细（读，只读不审批）

1. 用户问“这个文件里都有些什么数据”时，用 `device_health.list_metrics`：报指标名、条数、单位、起止日期。`activity_summary` 是设备自报的日合计条目数。
2. 用户追问明细（“把昨天的步数记录列出来”）时，用 `device_health.query_records`：`metric` 填 `steps` 这类规范名或 Apple 原类型名，`start`/`end` 填日期，`limit` 缺省 200（最多 1000）。返回 `truncated: true` 时明确说“只看了前 N 条”。
3. 不认识的指标类型不要跳过：原样报出 Apple 类型名和条数。

## 答复结构

- 日期：步数 X · 距离 Y km · 消耗 Z kcal · 锻炼 M 分钟 · 心率均值/区间
- 来源：本地文件路径；查询时间：本次查询的时间
- 有 watch 自报时加一行“设备自报”对照

## Common Rationalizations

| 借口 | 反驳 |
| --- | --- |
| “用户问健康数据，意思就是授权我联网去 Apple Health / 手环云端拉最新数据。” | 只能读用户给的本地导出文件。没文件就说没文件，不承诺也不尝试联网读取——实时设备通道尚未接入。 |
| “这天没数据，按他平时的量估一个报上去更省事。” | 没数据就是没数据。估算等于编造健康数据，绝不允许。 |
| “把原始文件发给外部 AI 服务分析一下更快。” | 数据不出机是硬边界。分析只能在本地做，不上传原始文件或解析结果。 |
| “summarize 报的数字和手表自报差一点，取个中间值更平滑。” | 两个来源都如实报出并标注来源，不自行调和。 |
