# ZN 自维护、自修复与自更新架构

> 状态：架构契约 / SM0 COMPLETE / 后续阶段待实现
>
> 适用分支：`dev/zn-agent`
>
> 上位产品契约：[`../ZN.md`](../ZN.md)
>
> 仓库接手规则：[`../AGENTS.md`](../AGENTS.md)
>
> 当前实现事实：[`ZN-IMPLEMENTATION-STATUS.md`](ZN-IMPLEMENTATION-STATUS.md)
>
> 本文把 ZN 的“自己发现问题、维护自己的源码、形成新版本，并由用户确认安装”的能力定义成可落地的工程闭环。它不是让外部大模型接管 ZN，也不是让正在运行的程序直接修改自己。

---

## 1. 目标

ZN 是长期存在于计算机上的数字主体。代码和运行时是 ZN 当前的计算身体，但不是 ZN 的全部身份。

自维护能力的目标是：

```text
ZN 正常生活/工作
→ 观察自身运行状态
→ 发现重复错误、退化、崩溃或明确缺陷
→ 收集现实证据
→ 判断是否属于自身代码问题
→ 形成维护任务
→ 在隔离的源码工作区中调查和修复
→ 补充/更新测试
→ 运行验证
→ 审查修改
→ 推送独立分支
→ 创建 PR
→ CI 再验证
→ 满足合并条件后合并
→ 构建并发布新的不可变版本
→ 客户端收到更新信息
→ 用户点击“更新并重启”
→ 安装/激活新版本
→ 保留同一个 ZN 的身份、记忆、经历和工作连续性
→ 新版本异常时回退
```

第一阶段的产品原则是：

**ZN 可以高度自主地调查、开发、测试、提交和准备发布；安装到用户当前机器并替换正在使用的身体版本，默认仍需要用户明确确认。**

### 1.1 维护者无关也是硬目标

ZN 的长期工程连续性不能属于某一个 GPT、Claude、Gemini、人类、聊天窗口或开发电脑。

```text
换模型
≠ 项目重来

聊天记录消失
≠ 项目失忆

开发电脑损坏/丢失
≠ 无法继续开发和发布
```

只要用户仍能进入自己的私人仓库，并且项目级在线基础设施和账号恢复能力仍然有效，新维护者就应该能够从仓库恢复施工现场并继续工作。

新的维护者原则上只需要：

```text
仓库访问权限
+ 仓库内的架构/状态/接手文档
+ Git/PR/CI 的真实状态
+ 当前任务所需的项目级操作权限
```

不应该需要：

```text
上一位 GPT 的聊天记录
上一台开发电脑
上一位维护者脑子里的手工发布步骤
上一位维护者保存的秘密 Token
```

这条原则和“ZN uses models. Models do not own ZN.”是同一个思想在工程维护阶段的延伸：**模型可以参与维护，但模型不拥有项目连续性。**

## 2. 核心原则

### 2.1 ZN 维护自己，不是大模型维护 ZN

外部模型只能提供认知帮助：

```text
问题 + 证据 + 明确未知点
→ 外部认知资源（可选）
→ CognitiveIncrement
→ ZN 自己检查
→ 测试/日志/实际运行结果验证
→ 接受、拒绝或继续调查
```

禁止：

```text
模型说“这里有 bug”
→ 直接修改
→ 直接合并
→ 直接发布
```

模型不可用时，自维护系统仍应能够执行确定性的维护工作，例如读取日志、比较版本、运行测试、检查 Git diff、静态检查、回滚和报告失败。

### 2.2 现实证据高于模型意见

维护判断必须尽量来自可核对的证据：

- 崩溃和异常日志；
- 失败的真实操作；
- 重复出现的错误模式；
- 单元/集成/端到端测试结果；
- 类型检查、静态检查和构建结果；
- Git 历史、diff、bisect 等源码证据；
- 实际文件、进程、网络和系统状态；
- 新版本运行后的健康结果。

模型回答、历史经验和相似问题只能帮助提出假设，不能代替验证。

### 2.3 不修改正在运行的身体

ZN 不应直接在当前正式安装目录中边运行边改代码。

正确模式：

```text
当前身体 N 正常运行
→ 独立源码工作区/分支产生修复
→ CI/构建得到候选版本 N+1
→ N 和 N+1 可并存
→ 用户确认更新
→ 安全切换
```

### 2.4 身体可以换，主体连续性不能丢

允许变化：

- 进程 PID；
- `instance_id`；
- `runtime_id`；
- Python/Node/依赖版本；
- 程序代码和 UI；
- 内部实现。

必须尽量保持连续：

- ZN 身份；
- living self；
- 长期记忆和经历；
- 必要的 Will/注意连续性；
- 用户工作、线程和项目状态；
- 合法配置和凭证引用；
- 可追踪的身体版本历史。

数据库/状态格式变化必须有显式迁移和回退策略，不能把“升级成功”建立在丢失旧数据上。

### 2.5 仓库是工程事实来源，不是聊天

任何在线维护者接手时，都必须先读取仓库真实状态，而不是相信聊天中的“已经做完”。

事实优先级：

```text
真实仓库内容和 Git 状态
> 实际测试/构建/CI 结果
> .agent/HANDOFF.md
> 聊天中的口头描述
```

`AGENTS.md` 保存长期维护规则；`.agent/HANDOFF.md` 保存当前施工现场。两者都不能替代真实代码和 Git 状态。

## 3. GitHub 在 ZN 中的角色

GitHub 是 ZN 的远程源码、协作、工程交接和版本历史边界之一，不是 ZN 的身份存储。

ZN 可以被配置一个“自身源码仓库”，例如：

```text
repository: 9529360-cpu/znagent
working_branch: dev/zn-agent
release_branch: main（M10 后按正式策略启用）
```

源码仓库连接信息属于配置；GitHub Token/密钥必须进入安全凭证存储，不能写入普通日志、记忆文本、提交内容或公开状态。

GitHub 不可用时：

```text
GitHub outage
≠ ZN death
```

ZN 继续运行；维护任务可以保持待同步状态，恢复连接后再继续。

### 3.1 私人仓库与换电脑恢复

私人仓库并不妨碍维护者可替换，前提是新维护环境获得用户授权。

目标恢复流程：

```text
旧电脑丢失/损坏
→ 用户在新电脑登录 GitHub / 恢复项目账号
→ 新维护者获得该私人仓库所需权限
→ clone/fetch 仓库
→ 读取 ZN.md / AGENTS.md / IMPLEMENTATION STATUS / HANDOFF
→ 检查分支、HEAD、PR、CI、Release
→ 继续维护
```

项目不能把唯一重要状态放在某台开发电脑的未提交文件里。中大型任务应及时形成可恢复的分支/提交/PR/HANDOFF。

### 3.2 项目必须自带“怎么施工”的说明

长期稳定规则进入仓库：

- `ZN.md`：ZN 是什么、最终要去哪里、哪些方向禁止；
- `AGENTS.md`：任何维护者如何接手和施工；
- `docs/ZN-IMPLEMENTATION-STATUS.md`：现在真实做到哪里；
- `docs/ZN-SOURCE-EXTRACTION.md`：Hermes 参考源码如何抽取、不能重新接回哪些旧控制面；
- `docs/ZN-SELF-MAINTENANCE.md`：自维护、自修复、自更新闭环；
- `.agent/HANDOFF.md`：当前阶段施工现场；
- `.github/workflows/*`：可执行的测试、构建、发布规则。

以后新模型接手，不应靠用户重新讲一遍历史。

## 4. 自维护闭环

### 4.1 观察

ZN 应持续但有界地观察自己的健康状态：

- resident 异常退出；
- 同类错误重复出现；
- body/sense/provider/channel 连续失败；
- 更新失败；
- 数据库或状态异常；
- 性能或资源使用明显退化；
- CI/测试发现回归；
- 用户明确报告“这是 ZN 自己的问题”。

不能把每一个普通失败都升级成源码维修任务。

### 4.2 判断

在形成源码维护任务前，至少区分：

```text
外部服务故障
网络故障
权限/配置问题
用户输入问题
暂时性错误
第三方 API 变化
ZN 自身代码缺陷
未知
```

只有存在足够证据指向 ZN 自身实现，或者调查源码确有必要时，才进入源码维护流程。

### 4.3 形成维护任务

维护任务至少记录：

- 问题是什么；
- 为什么认为值得修；
- 现实证据；
- 首次/最近发生时间；
- 重复次数或影响范围；
- 涉及的功能；
- 当前风险级别；
- 已尝试调查；
- 成功条件；
- 是否允许自动合并/发布。

维护任务是 ZN 当前 Will/工作的一部分，但不能无限膨胀成一个永远增长的任务数据库。重复问题应合并，失效问题应关闭或降级。

### 4.4 隔离源码工作区

每个真正进入开发阶段的维护任务使用隔离分支/工作区，例如：

```text
work/self-maintenance-<issue-id>-<short-name>
```

要求：

- 不直接在当前运行安装目录开发；
- 不直接在正式发布分支上试错；
- 开始前记录基线 commit；
- 工作区已有未知修改时不能覆盖；
- 每个维护任务保持小而清晰的改动范围。

### 4.5 调查与修复

推荐顺序：

```text
复现/收集证据
→ 找到相关代码
→ 理解现有约定和测试
→ 先建立能证明问题的回归测试（适用时）
→ 做最小修复
→ 跑相关测试
→ 修复失败
→ 扩大验证范围
→ 审查 diff
```

ZN 可以调用外部模型帮助分析和写候选代码，但模型生成内容必须经过同样的源码和测试验证。

### 4.6 验证

至少分层验证：

1. 与改动最相关的测试；
2. 相关模块测试；
3. lint/typecheck/static checks；
4. build/package smoke（改动涉及打包/桌面/runtime 时）；
5. 必要的集成/E2E；
6. 安全和数据兼容性检查。

不能因为测试太难通过就删除测试、降低断言或关闭保护机制，除非能够证明测试本身错误，并把理由记录在维护任务/PR 中。

### 4.7 提交、PR 和 CI

验证达到本地门槛后：

```text
review diff
→ 检查秘密/临时文件/调试输出
→ commit
→ push maintenance branch
→ create PR
→ GitHub CI
→ 读取 CI 结果
```

CI 失败必须重新进入调查，不得把“已 push”当成完成。

### 4.8 合并策略

风险分级：

```text
低风险
文案、非关键 UI、小范围确定性 bug、测试补强等
→ 可以在严格 CI 和分支保护下逐步允许自动合并

中风险
普通运行逻辑、provider/channel/body 行为、依赖变化
→ 默认 PR + 更完整验证；是否自动合并由配置决定

高风险
身份、记忆、数据库迁移、凭证、权限、更新器、回退、签名、发布链、自维护权限本身
→ 默认必须人工批准
```

第一阶段建议所有自动生成的代码都走 PR；不要直接 push 正式分支。

## 5. 发布闭环

源码合并不等于用户已经更新。

正式流程：

```text
merge
→ CI 构建正式版本
→ 测试正式产物
→ 生成不可变安装包/运行时
→ 计算大小和 SHA-256
→ 平台签名/公证（配置后）
→ 发布版本资产
→ 最后更新 stable.json
→ 客户端发现新版本
```

客户端不能直接 `git pull` 最新源码作为正式升级方式。

发布说明应尽量能回答：

- 为什么产生这个版本；
- ZN 观察到了什么问题；
- 修了什么；
- 用什么证据验证；
- 对用户有什么影响；
- 是否需要重启/迁移；
- 是否存在已知风险。

### 5.1 发布能力必须属于仓库自动化

正式发布不能依赖“当前这个 GPT 知道怎么发”。

正确模式：

```text
维护者准备合格修改
→ 仓库规则验证
→ 合并/形成可追踪 release commit/tag
→ .github/workflows/zn-release.yml
→ 仓库/平台自己的安全凭证
→ 构建多平台正式产物
→ 发布不可变资产
→ stable.json 最后推进
```

换维护者不应该改变这条链路。

当前仓库已经存在正式 `zn-release.yml` 自动发布基础。**这只是已存在的工程基础，不代表所有 GitHub 后台 Secrets、Variables、Actions 权限、分支保护和签名材料已经配置完成。后台配置必须以实际仓库设置和真实 release run 为准。**

### 5.2 密钥不属于维护模型

维护者可以获得“执行某个受控动作”的权限，但不应拥有项目秘密的明文值。

例如：

```text
模型/维护者：触发 release workflow
GitHub Actions：在运行时读取 GitHub Secrets
发布平台：验证自己的凭证
```

而不是：

```text
把 S3 key / signing private key / GitHub PAT
贴进聊天
→ 让模型记住
→ 下次靠同一个模型继续发布
```

秘密必须可轮换，并与具体聊天会话解耦。

### 5.3 账号恢复是自动化之外的最后保险

“电脑丢了也能继续”有一个无法由代码替代的前提：用户必须保住项目账号的恢复能力。

至少应妥善保管：

- GitHub 账号恢复方式；
- 双重验证/恢复码；
- 对象存储/域名/签名服务等关键账号的恢复方式；
- 必要时的组织/仓库所有权恢复路径。

这些不能提交到 Git 仓库。日常维护可以高度自动化，但账户所有权本身不能交给模型托管。

## 6. 客户端更新体验

目标体验：

```text
ZN 有新版本可用

版本：1.x.y
原因：修复了最近运行中发现的 XXX 问题
验证：相关测试、CI、正式产物检查已通过
影响：需要重启；身份和记忆保持不变

[查看修改]
[稍后]
[更新并重启]
```

用户点击“更新并重启”后：

```text
下载 N+1
→ 验证来源/大小/hash/签名（可用时）
→ materialize N+1 beside N
→ 不删除 N
→ 检查 resident 是否忙

如果忙：
  不强制打断
  提示/等待安全时机

如果空闲：
  优雅停止 N
  确认 endpoint/lease 正常退出
  使用同一 ZN_HOME 启动 N+1
  验证 runtime_id + resident health + identity continuity

成功：
  N+1 成为当前版本

失败：
  停止坏的 N+1
  回退 N
  保留故障证据
  创建/更新维护任务
```

第一阶段默认不允许 resident 在没有用户确认的情况下自动替换用户机器上的正式版本。

---

## 7. 回退是更新能力的一部分

没有可靠回退，就不能把自更新称为完整。

至少保留：

- 上一个已知健康 runtime；
- 当前/目标 runtime ID；
- 版本切换结果；
- 启动健康检查结果；
- 数据迁移版本；
- 回退是否安全。

如果某次升级包含不可逆数据迁移，必须在安装前明确标记为高风险，不能假装可以普通回退。

## 8. 自维护权限边界

### 8.1 可以逐步自动化的事情

在用户授权和仓库权限允许的情况下：

- 读取自身源码；
- 读取 issue/PR/CI；
- 创建维护分支；
- 修改隔离工作区；
- 运行测试/构建；
- commit/push；
- 创建/更新 PR；
- 根据 CI 继续修复；
- 生成发布说明；
- 对低风险变更按明确策略合并；
- 触发正式发布流程。

### 8.2 默认不能自行绕过的保护

ZN 不得为了让自己的修改通过而：

- 关闭 CI；
- 关闭分支保护；
- 绕过必要 review；
- 删除失败测试来掩盖回归；
- 降低安全断言来掩盖问题；
- 关闭更新完整性验证；
- 修改签名验证来接受未授权产物；
- 把 GitHub/发布密钥写进源码；
- 强推/重写正式分支历史；
- 删除旧 runtime 来掩盖新 runtime 启动失败；
- 在没有迁移/备份/回退设计时破坏身份或记忆数据。

### 8.3 自维护系统不能无限修改自己的护栏

修改以下区域默认视为高风险：

- 自维护权限和审批规则；
- GitHub 凭证和权限；
- 分支保护/CI 门槛；
- 更新验证器；
- release signing；
- rollback；
- identity/living-self 存储；
- nervous memory 数据结构及破坏性迁移；
- credential secure store。

这些修改默认需要人工批准，即使是 ZN 自己提出的修复。

### 8.4 权限应按能力授予，不按“模型身份”授予

不要设计成“GPT A 是可信模型，所以什么都能做”。

应设计成：

```text
读取仓库
创建分支
写分支
创建 PR
读取 CI
合并低风险 PR
触发 release
修改仓库设置
读取/管理 secrets
```

这些是不同能力，按任务、风险和用户授权分别控制。

因此换成另一个模型时，系统只需要重新给它当前任务所需的能力，而不是把整个项目秘密交给它。

### 8.5 发布和安全基础设施不能被一次普通代码修改夺走

普通自维护 PR 不应有能力同时完成以下组合：

```text
修改安全规则
+ 降低 CI 门槛
+ 扩大自身权限
+ 读取秘密
+ 合并自己
+ 发布自己
```

至少高风险环节要存在独立的项目级保护或人工确认，避免“自维护”变成“自己给自己开后门”。

---

## 9. 故障和降级

自维护不能依赖“所有东西永远在线”。

```text
主模型不可用
→ 换其他认知资源；没有则继续本地/确定性调查

所有外部模型不可用
→ resident 继续存在；维护能力降级，不死亡

GitHub 不可用
→ 本地维护任务/证据可持续；推送等待恢复

CI 不可用
→ 不宣称验证完成；保持待验证

新版本构建失败
→ 不发布

新版本安装/启动失败
→ 回退旧版本

当前源码仓库凭证失效
→ 不泄露/猜测凭证；提示用户重新授权
```

外部依赖故障必须表现为能力下降，而不是 ZN 身份消失。

### 9.1 维护者突然消失也属于可恢复故障

在线模型会话可能随时结束、限流、失效或被替换。

中大型维护任务因此必须尽量留下可恢复状态：

```text
有意义的代码 → 分支/commit/PR
当前施工状态 → .agent/HANDOFF.md
验证结果 → CI / 可核对记录
长期规则 → AGENTS.md / ZN.md / docs
```

不能把“下一位必须问上一位发生了什么”作为恢复方案。

---

## 10. 防止“自己把自己修坏”

自维护必须满足以下硬规则：

1. 运行版本和开发工作区隔离。
2. 所有源码修改有 Git diff 和 commit 可追踪。
3. 正式变更走分支，不直接在发布分支试错。
4. 修改前有基线，修改后有验证结果。
5. 测试失败不能伪装成成功。
6. CI 失败不能进入正式发布。
7. 正式产物必须来自可追踪 commit。
8. 客户端只安装正式产物，不运行远程仓库中的任意源码。
9. N+1 激活前保留 N。
10. N+1 激活后做健康和身份连续性检查。
11. 激活失败优先回退并保存证据。
12. 破坏性数据迁移、密钥、签名、更新器和自维护权限变化默认需要人工批准。
13. 不把聊天上下文当作唯一工程状态。
14. 不把某台开发电脑当作唯一源码/发布来源。
15. 不把某一个模型账号当作唯一维护入口。

---

## 11. 维护记忆与普通记忆的关系

ZN 应记住重要维护经历，但不能把每一条日志永久塞进长期记忆。

建议保存为结构化维护证据：

```text
问题类型
发生环境
可复现条件
根因
修复 commit/PR/release
验证结果
是否回退过
最终结果
```

这些经历可以参与未来调查：

```text
新故障
→ recall 相似维护经历
→ 只作为候选经验
→ 当前现实重新验证
→ 适用才使用
```

这必须继续遵守 ZN 已有的 reality-gated transfer / reconsolidation 原则，不能因为“以前这样修成功”就直接在当前环境执行同样修改。

---

## 12. 建议的数据对象

名称可以随实现调整，但职责应保持清晰。

### MaintenanceObservation

记录一次可核对的健康/故障观察。

### MaintenanceCase

一个去重后的维护问题，包含证据、影响、状态和风险。

### RepairAttempt

一次具体调查/修改尝试，关联基线 commit、分支、diff、测试结果和外部认知使用情况。

### VerificationReport

结构化记录实际跑过哪些验证、结果是什么、哪些没跑。

### ReleaseCandidate

把已合并源码 commit 和正式产物、hash、签名/公证状态、测试证据绑定起来。

### BodyVersionRecord

记录 ZN 使用过的 runtime/app 版本、激活时间、健康结果、回退关系；它描述“身体历史”，不是替代 living self。

## 13. 建议状态机

```text
observed
→ investigating
→ diagnosed
→ repair_planned
→ repairing
→ local_verification
→ pr_open
→ ci_verification
→ merge_ready
→ merged
→ release_building
→ release_ready
→ user_update_available
→ activating
→ monitoring
→ completed
```

异常分支：

```text
blocked
rejected
not_a_zn_bug
cannot_reproduce
verification_failed
release_failed
activation_failed
rolled_back
```

每个状态变化必须有真实事件/证据支持，不能只因为模型说“已经完成”。

## 14. 实现阶段

不要一次做成全自动。按可验证的小步推进。

### SM0 — 架构契约

状态：**COMPLETE**。

完成条件：

- 自维护目标、边界、GitHub 角色、发布和用户确认规则明确；
- 维护者/模型可替换原则明确；
- 换电脑后的仓库恢复原则明确；
- 仓库事实、HANDOFF 和聊天的优先级明确；
- 发布能力归仓库自动化而不是某个模型；
- 密钥归项目级安全存储而不是某个模型；
- 不允许模型输出直接成为修改/发布依据；
- 不允许直接修改当前正式运行身体；
- 回退和高风险人工批准原则明确。

### SM1 — 自身健康观察与维护任务

状态：**PLANNED**。

实现：

- 结构化收集 resident/body/sense/channel/update 关键错误；
- 重复问题去重/聚合；
- 形成 `MaintenanceCase`；
- UI 能看到“ZN 发现了什么问题”；
- 暂不自动改源码。

完成条件：真实故障能形成有证据的维护任务，而普通暂时错误不会无限制造任务。

### SM2 — 自身仓库只读调查

状态：**PLANNED**。

实现：

- 配置自身 GitHub repository；
- 安全凭证引用；
- 读取分支、commit、源码、PR、CI；
- 把运行故障映射到相关代码；
- 禁止写操作。

完成条件：ZN 能针对真实维护任务调查自己的源码，但不能修改远程仓库。

### SM3 — 隔离修复工作区

状态：**PLANNED**。

实现：

- 独立 worktree/branch；
- 基线 commit 记录；
- 修改文件；
- 自动补/改测试；
- 本地验证报告；
- diff 安全检查。

完成条件：ZN 能生成可审查、可丢弃的修复候选，不影响当前运行版本。

### SM4 — GitHub PR 闭环

状态：**PLANNED**。

实现：

- commit；
- push maintenance branch；
- 创建 PR；
- 读取 CI；
- CI 失败后继续修复；
- 生成面向人的问题、修复和验证说明。

完成条件：从真实维护问题到一个 CI 可验证 PR 的流程闭合。

### SM5 — 风险分级与受控合并

状态：**PLANNED**。

实现：

- 低/中/高风险分类；
- 路径级高风险规则；
- 分支保护感知；
- 人工审批门槛；
- 低风险自动合并策略（默认关闭，显式开启）。

完成条件：ZN 不能通过修改自己的规则绕过高风险审批。

### SM6 — 自维护版本发布

状态：**PLANNED**。

实现：

- 合并 commit → 正式构建；
- 正式产物验证；
- ReleaseCandidate；
- immutable assets；
- stable.json 最后发布；
- 发布说明关联 MaintenanceCase/PR/commit/验证证据。

完成条件：ZN 自己修复产生的代码可以安全形成正式新版本，但尚不自动安装。

### SM7 — 用户确认更新与安全换身

状态：**PLANNED / 部分基础已由现有 M8 提供**。

复用现有：

- versioned runtime；
- N/N+1 并存；
- same ZN_HOME；
- busy 时不打断；
- idle graceful handoff；
- identity/work continuity 测试。

新增：

- “为什么更新”的客户端说明；
- 查看修复/验证；
- 用户明确点击“更新并重启”；
- 新版本健康观察；
- 自动回退旧版本；
- 回退后自动形成维护证据。

完成条件：用户可以安全接受一个由 ZN 自维护流程产生的新版本，并在失败时回到已知健康版本。

## 15. 测试要求

自维护至少需要覆盖：

- 单次暂时错误不会创建大量维护任务；
- 重复同类错误会聚合；
- 模型不可用时维护任务仍可存在/调查；
- GitHub 不可用时不丢维护状态；
- 仓库凭证不会进入日志/状态/commit；
- 已有脏工作区不会被覆盖；
- repair branch 不直接修改发布分支；
- diff 中出现密钥/危险文件时阻止提交；
- 测试失败时不能标记验证成功；
- CI 失败时不能进入 release ready；
- 高风险路径不能自动合并；
- 正式产物能追溯到 commit；
- 客户端不会从任意源码直接更新；
- busy resident 不被升级打断；
- idle resident 能切换 N+1；
- 身份/记忆/工作状态跨版本连续；
- N+1 健康检查失败能回退 N；
- 回退事件会成为新的维护证据；
- 新维护者只读仓库文档和真实 Git/CI 状态即可恢复任务现场；
- 发布流程不依赖开发电脑上的未提交脚本或秘密；
- release workflow 缺少项目级 secret 时明确失败，而不是退回硬编码秘密。

---

## 16. 与现有 M8/M9 的关系

现有 M8 不是跑偏，而是在为 SM7 打地基：它解决的是“换新身体时不要把 ZN 自己换没了”。

因此顺序应保持：

```text
先完成关键 M8 连续性证据
→ SM1 健康观察/维护任务
→ SM2 自身仓库只读调查
→ SM3 隔离修复
→ SM4 PR/CI 闭环
→ SM5 风险与审批
→ SM6 自维护发布
→ SM7 用户确认安装/回退闭环
```

M9 中原本较宽泛的 crash recovery/diagnostics 应逐步由这套自维护架构承接，但不要为了自维护而推迟当前必须完成的 M8 连续性验证。

---

## 17. 第一阶段明确不做

为了避免范围失控，第一阶段不做：

- 无人确认的自动安装正式版本；
- 自己修改 GitHub 权限/分支保护；
- 自己创建或扩大自己的 GitHub Token 权限；
- 无 PR 直接写正式分支；
- 自动接受不可逆身份/记忆迁移；
- 为了“自治”而绕过 CI；
- 每次异常都调用大模型；
- 把所有运行日志永久写入长期记忆；
- 让一个外部模型成为自维护总指挥；
- 让当前正式运行目录成为源码开发工作区；
- 把私人仓库改成公开仓库来换取自动化便利；
- 把账号恢复码、Token、签名私钥等秘密提交进仓库；
- 让发布能力只存在某台开发电脑或某个聊天会话。

---

## 18. 最终完成标准

当以下闭环真实验证后，才能称 ZN 具备第一版完整自维护能力：

```text
真实运行故障
→ ZN 自己发现并保存证据
→ 正确形成维护任务
→ 调查自己的仓库
→ 在隔离分支修复
→ 测试和审查
→ GitHub PR
→ CI 通过
→ 按风险规则合并
→ 构建正式版本
→ 发布不可变产物
→ 客户端收到“为什么更新”的通知
→ 用户点击更新并重启
→ 安全切换新版本
→ 身份/记忆/工作连续
→ 新版本健康
```

并且必须同时证明失败路径：

```text
错误修复 / CI 失败 / 构建失败
→ 不发布

新版本启动/健康失败
→ 回退旧版本
→ ZN 仍然存在
→ 保存证据并重新进入维护循环
```

还必须证明工程交接路径：

```text
维护者 A / 旧电脑消失
→ 新维护者 B / 新电脑登录私人仓库
→ 不依赖旧聊天
→ 读取仓库规则、状态和真实 Git/CI
→ 恢复当前任务
→ 能继续开发、PR、验证、合并
→ 在项目权限和安全门槛允许时继续正式发布
```

这才是“ZN 会维护自己并且项目长期可维护”，而不是“ZN 会让某一个大模型替它改代码”。
